## System Overview

Fastify + Prisma + PostgreSQL + Redis backend for "Lib" (product name: EuZerei), a personal game-library tracker. Frontend is a separate React+Vite repo (`lib-front-end`), out of scope here. Layered: routes → controllers → services → repositories → Prisma/Postgres, with Redis as cache, rate-limit store, short-lived token store and BullMQ backend. IGDB is the game-data provider; Steam, PlayStation and Xbox libraries are imported by background jobs. No DI container: each route file wires its own controller/service/repository graph.

## Auth Flow

- **Cookies**: `accessToken` (httpOnly, secure, sameSite lax, 15min), `refreshToken` (httpOnly, secure, sameSite lax, 7d). Set and cleared with the same options in `src/utils/auth-cookies.ts`. `secure: true` is hard-coded. `sameSite: lax` is what lets the OAuth, Steam and Xbox GET callbacks (cross-site top-level redirects) carry the session.
- **`app.authenticate` decorator** (src/jwt.ts): verify the access token → reject a refresh token used as access → check revocation (Redis `revoked:${hash(accessToken)}`, then `sessions-revoked-at:${userId}` against the token's `iat`); a Redis failure here answers 503, it does not fail open. Only a missing access cookie (`FST_JWT_NO_AUTHORIZATION_IN_COOKIE`) triggers the silent renewal through the `refreshToken` cookie, with no rotation (rotation only happens on explicit `/auth/refresh`); the cookie's max-age equals the JWT lifetime, so an expired token is simply absent. Any other failure is 401.
- **`app.tryAuthenticate`**: optional auth for the `/games` listings. Never refreshes, never clears cookies, never answers; an invalid or revoked token, or a revocation check that cannot be made, just leaves the request anonymous.
- **Email normalization**: emails are always stored and compared in lowercase. `EmailSchema` trims and lowercases on signup, login and password reset; `normalizeEmail` (`src/utils/normalize-email.ts`) does the same to the address a provider returns. No provider-specific rules (Gmail dots, plus addressing). The original casing is not kept.
- **Password auth**: bcrypt hash (cost 12), generic "Email ou senha incorretos." on any mismatch (doesn't leak which field), with a dummy hash compared when the user does not exist to equalize timing. Password policy (`src/schemas/auth.schema.ts`): 8+ characters, at most 72 UTF-8 bytes (bcrypt's limit), not in the built-in common-password list, not equal to the email or its local part.
- **Google/Discord OAuth**: `@fastify/oauth2` registered but its helpers are bypassed — routes hand-roll state generation (stored in Redis, `oauth-state:${state}`, TTL 600s, single-use), manual authorize URL construction, and a manual `fetch` token-exchange fallback if the plugin's method fails. OAuth users get a throwaway random bcrypt password (schema requires non-null `password`). OAuth errors redirect browser to `${FRONTEND_URL}/auth?error=oauth_failed` (not JSON).
- **OAuth email trust**: an account is only created or linked by email when the provider reports the email as verified (`email_verified` on Google, `verified` on Discord); otherwise the browser is redirected with `?error=email_not_verified`. Linking a provider to an account that has no other provider replaces its password with a random one and revokes its sessions, even when the email was verified by link: clicking the link proves control of the mailbox, not who chose the password. Any provider link or sign-up marks the account verified. A provider login whose email matches an account already linked to a different account of that same provider is refused (409, redirected as `oauth_failed`) instead of replacing the link.
- **Email verification**: signup sends a link (`${FRONTEND_URL}/verify-email?token=...`, 24h, single-use). Only the sha256 of the token is stored in Redis (`email-verification:${hash}`), with `email-verification-current:${userId}` so a new link invalidates the previous one, and `email-verification-requests:${userId}` limiting resends to 3 per hour. Unverified accounts use the app normally; a password reset by link also marks the account verified. Delivery failure never breaks signup (logged, with the link printed outside production). `GET /users/me` returns `email` and `emailVerified`. Migration backfill: accounts with `google_id` or `discord_id` start verified, password-only accounts do not.
- **Session revocation**: password reset, the link takeover above and account deletion delete every refresh token of the user and set Redis `sessions-revoked-at:${userId}` (TTL 15min); `app.authenticate` rejects access tokens issued before that cutoff. `DELETE /users` also clears the auth cookies.
- **Steam link** (proof of ownership): `POST /users/steam/openid` returns the Steam OpenID login URL; Steam returns the browser to `GET /users/steam/openid/callback`, which checks the single-use state (Redis `steam-link-state:${state}`, bound to the user), validates the assertion with Steam (`check_authentication`) and redirects to `${FRONTEND_URL}/userLibrary?steam=connected|taken|failed`. Requires `STEAM_OPENID_RETURN_URL`: the callback URL as the browser reaches it, on the host that holds the session cookies.
- **PSN link** (proof of ownership): `POST /users/psn/verification` issues a one-time code (Redis `psn-verification:${userId}`, TTL 15min); `PATCH /users/psn` links only if the code is in the profile's "About me".
- **Xbox link** (proof of ownership): `POST /users/xbox/oauth` returns the Microsoft sign-in URL (`XboxLive.signin` scope); Microsoft returns the browser to `GET /users/xbox/oauth/callback`, which checks the single-use state (Redis `xbox-link-state:${state}`, bound to the user), exchanges the code and walks Xbox Live auth (user token → XSTS) to read the XUID and gamertag, then redirects to `${FRONTEND_URL}/userLibrary?xbox=connected|taken|no_profile|failed`. Requires `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` and `XBOX_OAUTH_CALLBACK_URL` (the callback as the browser reaches it, registered as redirect URI in the Azure app). OpenXBL is still used for the import itself.
- **Login lockout** (`AuthService.validateUser`): failures are counted per email+IP (`login-failures:${hash(email)}:${hash(ip)}`, limit 10) and per email (`login-failures:${hash(email)}`, limit 50), both with a 15min window; either one over its limit answers 429 before bcrypt runs. The per-email limit only applies to unfamiliar IPs: a successful password login stores `login-familiar-ip:${hash(email)}:${hash(ip)}` for 30 days, and a familiar IP is checked and counted only against its own email+IP limit, so failures from elsewhere cannot lock it out. Success clears only the email+IP counter; a password reset clears both. A block is logged as `[Login] blocked` with the scope only.
- **Sessions**: each login/OAuth sign-in creates its own refresh token row. Logout invalidates only the cookie's token; password reset and provider takeover call `revokeAllSessions`.
- **`TRUST_PROXY`**: unset trusts no proxy. Behind a reverse proxy set the hop count (e.g. `1`) or the proxy IPs/CIDRs, otherwise rate limits see the proxy's IP for every client.

## Platform Imports (Steam, PlayStation, Xbox)

**Flow, the same for the three platforms**: `POST /users/<platform>/import` → `XService.enqueueImport` → `enqueueUniqueImport` (`src/queues/import-job.ts`) adds a job to the platform's BullMQ queue → the worker (started in `Server.start()`, same process as the API, concurrency 1 per queue) calls `XService.runImport(userId, onProgress)` under a 5 minute timeout → each game goes through `UserGamePlatformService.importPlatform`. `GET /users/<platform>/import` reads the job: `idle`, `waiting`/`active`/`delayed` (with `progress`), `completed` (with `result` and `cooldownUntil`) or `failed` (with `error`).

- **Queues**: `steam-import`, `psn-import`, `xbox-import`. Job id `<platform>-import-${userId}`.
- **One at a time, 1 hour cooldown**: a waiting/active/delayed job answers 409; a job completed less than 1 hour ago answers 429 with the minutes left; a failed job can be retried at once. Jobs are never auto-removed: the finished job kept in Redis is what the cooldown reads.
- **Result**: `{ library: { imported, updated, skipped, notFound[] } }`; Steam adds a `wishlist` section of the same shape.
- **Errors**: only `ClientError` messages reach the user; anything else is logged and replaced by a generic message. The timeout fails the job but does not cancel the work already running.

| | Steam | PlayStation | Xbox |
|---|---|---|---|
| Proof of ownership | OpenID assertion | code pasted in the profile "About me" | Microsoft OAuth → Xbox Live → XSTS |
| Data source | Steam Web API (`STEAM_API_KEY`) | `psn-api` with a service account (`PSN_NPSSO`) | OpenXBL (`OPENXBL_API_KEY`) + Microsoft catalog |
| Matched to IGDB by | Steam app id (source 1) | concept id (source 36) | Store product id (source 11), then a name search fallback |
| Hours | `playtime_forever` | summed play minutes per concept | `MinutesPlayed` stat (import continues without hours if it fails) |
| Also imports | the wishlist, as WISHLIST, skipping games already in the library | nothing else | nothing else |
| Provider limits (not enforced in code) | not known | about 300 calls per 15 minutes on the service account | OpenXBL: 150 requests per hour; a 429 from it becomes a 503 |

**Completion detection** (`src/utils/completion-heuristics.ts` + each service). Two signals per game:
- `finished`, a heuristic: a rare achievement (5% or less of players, only when the game has at most 100 achievements), or an achievement whose description matches end-of-game wording (`COMPLETION_KEYWORD_PATTERN`), or an earned/total ratio above a threshold that shrinks as the total grows (90% up to 10 achievements, down to 15% above 150; never with fewer than 5). Only inferred for games with a single-player mode that are not sport or racing (`canInferCompletion`).
- `confirmedFinished`, a fact: every achievement (Steam, with at least 5; Xbox, `achievementProgress >= 100`) or the platinum / 100% of trophies (PSN).
- `activityStatusId`: PLAYING when played in the last 14 days, otherwise BACKLOG.

**What `importPlatform` does** (`src/services/user-game-platform.service.ts`):
- New game: enters with the heuristic (`PLAYED` when `finished`, otherwise the activity status).
- Game already in the library: only `confirmedFinished` moves it to PLAYED; otherwise it can only move up to the activity status. The status never goes down. Rank, lowest first: WISHLIST, BACKLOG, PAUSED, PLAYING, PLAYED.
- Platform row: hours are overwritten with the platform's value; a completion and its date are only added (never removed or overwritten), and for an existing game only when confirmed.
- Steam only fetches achievements for games with playtime and `canInferCompletion`, so a multiplayer-only game at 100% is never confirmed.

## IGDB Integration

`IGDBService` is a static-only class. Token: Twitch client-credentials, cached in process memory (not Redis), refreshed 60s before expiry.

Three tiers of game data:
1. **Live IGDB API**: game detail, similar games, coming soon, recently released, metadata for ranked ids.
2. **`games_cache` in Postgres**: the mirror used for listing, search, sort and for joining metadata onto library rows. Filled by `npm run sync:igdb` (resumable, ascending id) and 5 backfill scripts; also filled on demand by `GameCacheService.ensureCached` (library add, rating) and `cacheMany` (imports, library gaps).
3. **Redis cache-aside**, TTL 3600s:

| Method | Source | Redis key |
|---|---|---|
| `findAllGames` (browse/search) | `games_cache` | none |
| `findGameById` | live IGDB | `game:${igdbId}` |
| `findSimilarGames` | live IGDB | `game:similar:${igdbId}` |
| `findRecentlyReleasedGames` | live IGDB | `games:recent:${limit}` |
| `findComingSoonGames` | live IGDB | `games:comingSoon:${limit}:${pageIndex}` |
| `findTrendingGames` / `findMostRatedGames` | ranking from Postgres on every request, never cached | metadata per id in `game:meta:${id}` |

Ratings (cross-user average) and the caller's library data are never cached; they are read from Postgres and merged on every request. The personal rating and the cross-user average are always two separate values.

**External ids** (`getGamesByExternalIds`): queries the `external_games` endpoint by `uid` and `external_game_source` in chunks of 500, then fetches the games. Sources: 1 Steam, 36 PlayStation, 11 Xbox.

**"Released" cutoff**: the next midnight in `America/Fortaleza`. **`release_dates` dedup**: one row per platform+region; the detail endpoint groups by platform and keeps the earliest date.

| `revoked:${hash(accessToken)}` | access token revoked at logout | token's remaining life |
| `sessions-revoked-at:${userId}` | cutoff for every access token of a user | 15min |
| `recent-auth:${userId}` | login is recent enough to delete the account | 10min |
| `login-failures:${hash(email)}[:${hash(ip)}]` | lockout counters | 15min |
| `login-familiar-ip:${hash(email)}:${hash(ip)}` | IP that logged in successfully | 30d |
| `password-reset:${hash(token)}`, `password-reset-requests:${hash(email)}` | reset token, request limit | 1h |
| `email-verification:${hash(token)}`, `email-verification-current:${userId}` | verification token, pointer to the current one | 24h |
| `email-verification-requests:${userId}` | resend limit | 1h |
| `oauth-state:${state}`, `steam-link-state:${state}`, `xbox-link-state:${state}` | single-use state of the redirect flows | 10min |
| `psn-verification:${userId}` | pending PSN ownership code | 15min |
| `psn:access-token`, `psn:refresh-token` | PSN service-account tokens | provider expiry minus 60s |
| `idempotency:${userId}:played-count:${igdbId}:${key}` | replay protection of the completions PATCH | 60s |
| `bull:*` | BullMQ queues and retained jobs | none |

`CacheRepository.increment` is one Lua script (INCR, plus EXPIRE when the key is new or has lost its TTL), so a counter can never be left without expiry.

## Error Handling

Single global handler (`app.setErrorHandler`), no per-route try/catch:

| Error | HTTP | Body |
|---|---|---|
| `ClientError` (status set per throw site, default 400) | as specified | `{ message }` |
| `IGDBRequestError` | 502 | `{ message: 'Upstream game data provider failed' }` (details only in the log) |
| `ZodError` | 400 | `{ message: 'Invalid input', error: field errors }` |
| Fastify 4xx (rate limit, payload, unknown route...) | same status | generic `{ message }`, for example `Too many requests` |
| anything else | 500 | `{ message: 'Internal server error' }` |

Exceptions: the auth decorators answer `{ status: 'unauthorized' | 'unavailable' | 'reauth_required' }`, and the OAuth / Steam / Xbox callbacks redirect to the frontend with a result code in the query string, because the browser navigates to them directly.

## Non-obvious behaviour

Reasons that are not visible in the code. The code has no explanatory comments; this section is where that knowledge lives.

1. **Global rate limit is 300/min, not the usual 100** (`src/server.ts`). It was raised because TanStack Query refetches several query keys after each mutation and the import status is polled; 100 per minute was too tight for one person using the app normally.
2. **BullMQ has its own Redis connection** (`src/queues/connection.ts`). BullMQ needs a connection that is not shared with ordinary commands, created with `maxRetriesPerRequest: null`, because of its blocking commands.
3. **The job id is the "one import at a time" lock** (`src/queues/*-import.queue.ts`, `src/queues/import-job.ts`). The id is deterministic per user; `enqueueUniqueImport` looks the job up by that id and refuses a new one while it is waiting, active or delayed.
4. **Steam answers by shape, not by status** (`src/services/steam-api.service.ts`).
   - `GetOwnedGames`: a private profile (or a wrong SteamID) returns an empty `response` object with no `games` key. That missing key is the only signal Valve gives, and it is what turns into "make your profile public".
   - Wishlist: a missing `items` key means it could not be read; an empty array is a real, empty wishlist.
   - `GetPlayerAchievements`: `success: false` means the game has no achievement schema at all (most multiplayer-only titles), so there is nothing to infer from.
5. **IGDB external ids** (`src/services/igdb.service.ts`).
   - `external_games.category` is deprecated and always empty. The field in use is `external_game_source`, a reference into `external_game_sources`; id 1 is Steam (confirmed by querying that endpoint).
   - `external_games` is a reverse multi-relation on `games`, so it cannot be filtered with `where external_games.uid = (...)` on the `games` endpoint. The mapping uid → game id has to be read from the `external_games` endpoint first, and the games fetched after.
6. **Which cached games are listed** (`src/repositories/game-cache.repository.ts`). A game is notable enough to appear in listings and search when it clears either bar: at least 10 ratings (covers classics, which rarely have hype) or at least 5 hypes (covers announced games with no ratings yet).
7. **`category` and the `-1` sentinel** (`src/schemas/game.schema.ts`, `src/repositories/game-cache.repository.ts`, `src/services/games.service.ts`).
   - `category` is the IGDB id (0 main game, 1 DLC, 2 expansion, 8 remake, 9 remaster...) or `-1` when IGDB has none, which is common even for real DLCs and remasters.
   - `category` is always written, real id or `-1`, so `category IS NULL` in `games_cache` reliably means "not backfilled yet" and matches each row only once.
   - `parentGameId` being present is the reliable sign of DLC or related content, since `category` is often missing even then.
   - `parentGame` (the object) only comes on the single-game detail endpoint; listings carry just `parentGameId`.
   - The detail endpoint returns `game_type ?? category ?? -1` (IGDB is replacing `category` with `game_type`), while `games_cache` stores only `category`, so the two can differ for the same game.
8. **Moving a game to the wishlist deletes its rating** (`src/services/users.service.ts`). Wishlist means "not played yet"; a rating left there would be an opinion that no longer makes sense.
9. **Silent session renewal does not rotate the refresh token** (`src/services/auth.service.ts`, `isRefreshTokenActive`). It is a read-only check used by `app.authenticate`; rotating here would replace the refresh token every 15 minutes. Rotation happens only on `POST /auth/refresh`. At logout the access token is revoked inside an empty `catch`: the intent is to ignore a token that is already invalid or expired (nothing left to revoke), but the same `catch` also hides a Redis failure while storing the revocation.
10. **`tryAuthenticate` treats any problem as "anonymous"** (`src/jwt.ts`). The public listings must keep working for a visitor with a bad or expired cookie. This includes a Redis failure during the revocation check, which is not logged; `authenticate` answers 503 in the same situation.
11. **Rating a game changes the library** (`src/services/rating.service.ts`). A game that is not in the library is added as PLAYED with one completion; a WISHLIST game moves to PLAYED. Other statuses are left alone. Deleting the rating does not undo it.

## Conventions

- Controllers parse Zod → call one service method → shape the reply. Services own business rules and cache decisions. Repositories are the only place that touches Prisma or Redis.
- Raw `Prisma.sql` only where Prisma Client cannot express the query: the library listing (`findManyGamesOfUser`), listing by average rating (`findManyByRating`) and community reviews (joins + aggregates + dynamic sort).
- Zod schemas do double duty: `.parse()` in the controller is the validation gate; `schema.response` in the route mainly drives typing and serialization.
- User-facing messages are in Brazilian Portuguese; code and logs in English.
- No explanatory comments in the code. Reasons go in this file (Non-obvious behaviour) or in the commit message. The four `eslint-disable-next-line` directives stay.
- Emails are stored and compared in lowercase. Secrets and one-time tokens are stored as sha256 hashes, never in clear.

## Gotchas

1. **`prisma/seed.ts` is broken** and is the seed `package.json` points to. It calls `prisma.platform`, `prisma.game` and `prisma.gameLauncher`, which no longer exist, so `prisma db seed` fails. It is also the only place that creates the 5 `users_games_status` rows: a brand-new database has none, and adding a game fails until they exist.
2. **`prisma/seed-test-users.ts` works** but has no npm script, needs `games_cache` filled first and assumes the status rows exist.
3. **No `build` / `start` script**: the app only runs through `tsx`. No `outDir` in `tsconfig.json`, no Dockerfile, no CI.
4. **`unique-username-generator` is a devDependency used at runtime** (`src/services/auth.service.ts`). An install without dev dependencies breaks signup.
5. **Workers run inside the API process** and there is no graceful shutdown or health route. A restart in the middle of an import cuts the job.
6. **`Server.start()` is not awaited** in `src/index.ts`: a missing required variable shows up as an unhandled rejection. Required at startup: `REDIS_URL`, `SECRET_JWT_KEY` (32+ characters), `FRONTEND_URL`, the six Google and Discord OAuth variables, `DATABASE_URL`. Missing Steam, Xbox or SendGrid variables only fail when the feature is used (503, or the email is not sent).
7. **`.env` is not tracked by git** (`.gitignore` excludes it; only `.env.example` is tracked). `prisma/dev.db`, an old SQLite file with test data, is still in the git history of the public repository: a known and accepted risk.
8. **`@fastify/oauth2` is registered but barely used.** The Google and Discord routes build the authorize URL and manage the state by hand; the callbacks try a plugin method first and fall back to a manual `fetch`.
9. **In-memory IGDB token**: process-local, so several instances would each fetch their own.
10. **`tryAuthenticate` never refreshes.** A visitor whose access cookie expired but whose refresh cookie is valid is anonymous on `/games/*` until an authenticated route renews the session. `GET /games/:igdbId` has no optional auth at all.
11. **`GET /users/userGames` is only paginated with a `filter`.** Without one it returns the whole library grouped by status.
12. **`GameCacheRepository.upsertMany` never updates** (it is `createMany` with `skipDuplicates`), despite the name.
13. **Game-level stats vs platform rows.** With platform rows present, hours, completions and the completion date are recomputed from them and the game-level endpoints answer 400. `recomputeTotals` never clears `userGame.completedAt`.
14. **Import of an existing game sets two different dates.** When a confirmed completion moves an existing game to PLAYED, `updateGameStatus` stamps the library date with "now" while the platform row keeps the real date.
15. **Provider link is not atomic.** `loginWithGoogle` / `loginWithDiscord` discard the password and sessions before writing the link; if the link write fails the account is left with neither until the user retries or resets the password.
16. **Hard-coded status ids** (1, 3, 4, 5) are repeated as local constants in six services. Reseeding the lookup table in another order would silently break them.
17. **Dead or stale bits**: `UserGameStatusService.itemsPerPage`; the `fastify.d.ts` entry in `tsconfig.json` `include` (the file is `src/types/fastify.d.ts`); `main: "index.js"` and the `allowScripts` versions in `package.json`; the obsolete `version` key in `docker-compose.yml`.
18. **`docs/redis-caching.md` is stale.** It reads as a proposal and says there is no rate limiting or token revocation; all of that exists (see Redis Usage).
19. **`GET /rating/` can fail on a user without a name**: the response schema requires `userName` as a string and the column is nullable.
20. **Link expiry is written twice**: the email texts say "1 hora" and "24 horas"; the real limits are constants in `src/services/auth.service.ts`.

## Navigation Guide

- **Add an endpoint**: route in `src/routes/`, controller method (parse Zod, call the service), service method (rules, cache), repository method (Prisma Client; raw SQL only when a join or aggregate needs it). Add it to the Full Route Map here.
- **Change auth**: `src/jwt.ts` (decorators, plugins) → `src/services/auth.service.ts` (rules) → `src/repositories/auth.repository.ts` → `src/routes/auth.ts` (the OAuth redirect flows live in the route file) → `src/utils/auth-cookies.ts`, `src/utils/session-revocation.ts`.
- **Change an import**: `src/services/<platform>.service.ts` (matching, signals) → `src/utils/completion-heuristics.ts` (thresholds) → `src/services/user-game-platform.service.ts` (what a signal is allowed to change) → `src/queues/import-job.ts` (cooldown, one at a time).
- **Change the shape of game data**: `src/services/igdb.service.ts` (queries, `toGameCacheInput`) → `src/services/games.service.ts` (`formatGame`) → `src/schemas/game.schema.ts`. Read item 7 of Non-obvious behaviour before touching `category`.
- **Change the `games_cache` schema**: `prisma/schema.prisma` → migration → `GameCacheRepository` → `IGDBService.toGameCacheInput` → a backfill script if existing rows need the new column.
- **Add a sync or backfill script**: copy the pattern in `src/scripts/` (batch of 500, 300ms pause, resumable cursor, `$disconnect` at the end) and register it as `npm run backfill:*`.
- **Send a new email**: template in `src/services/email.service.ts`; delivery failures must not break the request unless the user explicitly asked for the email.
